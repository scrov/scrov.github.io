## Software Engineer · Fullstack Web · SSR/PWA · Realtime Systems

> Engineering portfolio presented as a living technical specification.

I design web systems around **clear contracts, composable boundaries, observable runtimes, and documentation that stays close to the code**.

The portfolio is intentionally built as a documentation system: Markdown and MDX form the authoring layer, **unified** supplies syntax-tree processing, **Astro** renders static or server-rendered content, **Angular** owns application UX, **NestJS** exposes typed backend capabilities, **EJS** handles server-side view composition where appropriate, and **Storybook** turns components into executable documentation.

## Angular SSR + PWA

Angular is the application layer for interactive product experiences. The SSR shell should remain thin: route resolution, initial state, accessible markup, and hydration boundaries belong near the rendering edge; domain behavior belongs behind services and application ports.

```text
Browser request
      │
      ▼
Astro shell / SSR route
      │
      ▼
Angular application
      │
      ├── signals / state
      ├── route data
      ├── API client
      └── service worker
      │
      ▼
NestJS API
```

The Angular + NestJS pairing is well suited to a monorepo when shared contracts and utility libraries need to stay synchronized across frontend and backend boundaries.

## Astro as the document host

Astro supports Markdown directly and can add MDX through `@astrojs/mdx`, enabling Markdown content to contain JSX expressions and components. Its content collections can also load local Markdown or MDX entries through build-time loaders.

That makes the wiki model straightforward:

```text
src/content/wiki/
├── index.mdx
├── architecture.mdx
├── api.mdx
├── ssr.mdx
├── storybook.mdx
└── templates.mdx
```

## unified document pipeline

`unified` is the content-processing boundary. The portfolio treats prose like source code: parse it, transform it, validate it, then serialize it for the target runtime. Its transformer model is centered on syntax trees and supports asynchronous transformations through promises.

```text
MDX / Markdown
      │
      ▼
mdast / hast
      │
      ├── lint
      ├── normalize
      ├── enrich metadata
      ├── generate anchors
      └── validate links
      │
      ▼
Rendered documentation
```

## MDX composition

MDX is used where documentation needs behavior or imported UI. It supports embedded components and injected component mappings, so the same authored document can become an interactive documentation page instead of a static wall of prose.

```mdx
# Component contract

<details>
  <summary>Open runtime notes</summary>

  The interface is documented beside the implementation.
</details>
```

For the Astro site, keep the MDX source portable and push site-specific layout into wrappers and components. This avoids coupling the CV text to one renderer.

## Storybook as executable documentation

Storybook MDX supports documentation alongside component stories, and its docs tooling can render imported Markdown as part of a documentation page. Angular projects can configure Storybook with the Angular framework adapter and options for styles, assets, source maps, and related integration concerns.

```mdx
import { Meta } from '@storybook/blocks';

<Meta title="Portfolio/Architecture" />

# Architecture

The component contract is documented beside the rendered story.
```

## EJS boundary

EJS belongs at the server/template boundary. It should render data already prepared by application services rather than accumulating business logic inside views.

```ejs
<main class="terminal-panel">
  <h1><%= profile.title %></h1>
  <p><%= profile.summary %></p>
</main>
```

That separation keeps EJS useful for server-oriented presentation while MDX remains the documentation/content format.

## Delivery blueprint

### Phase 1 · Contract

`README.mdx` defines the public narrative and links to stable wiki nodes. `openapi.yaml` defines machine-readable HTTP contracts.

### Phase 2 · Documentation runtime

Astro owns the published documentation route. MDX files become the canonical authored pages, with content collections providing typed metadata and predictable loading.

### Phase 3 · UI system

Angular owns interactive application surfaces. Storybook owns the component laboratory and executable documentation.

### Phase 4 · Backend

NestJS exposes domain modules and application services through explicit controllers and providers.

### Phase 5 · Integration

A CI pipeline validates Markdown/MDX, OpenAPI, TypeScript, Storybook builds, and the Astro site before publication.
